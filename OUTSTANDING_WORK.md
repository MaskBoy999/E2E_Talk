## R2. PQ ships, and A5 (the re-keying sweep) must be added and tested

**Requirement:** post-quantum envelopes and login **do** ship. Lazy re-keying is **not**
acceptable — the sweep must exist and be covered by a test.

**What already exists (verified in `origin/test`):**

- Hybrid key envelopes: X25519 + ML-KEM-768, packed `v2:` ciphertext, `v1` still readable.
  `server/src/db.rs` `encrypt_notification_payload`, `static/crypto.js` `envelopeEncrypt`.
- Hybrid login: Ed25519 + ML-DSA-65 over a server nonce. `server/src/main.rs`
  `verify_login_signature` / `decode_login_key_set` / `verify_ml_dsa_65`.
- Cross-language KATs: `server/tests/fixtures/pq-kat.json`, generated by
  `tools/gen-pq-kat.mjs`, asserted by Rust (`server/src/main.rs`) **and** in the browser by
  `tests/pq-envelopes.spec.ts`.
- Hybrid TLS: `tests/pq-envelopes.spec.ts` asserts `openssl s_client -groups X25519MLKEM768`
  negotiates the hybrid group.
- **Envelope half of the sweep already works:** `static/chat.js`
  `publishIdentityPqKeyIfNeeded()` runs on the heartbeat, compares
  `identity_pq_public_key`, and POSTs `/api/identity/pq-key` when it differs. Derived
  deterministically, so it is idempotent across devices.

**DONE (2026-11-07) — the login half was implemented. The historical gap, for the
record:** a v1 (bare Ed25519) account never upgraded:

| Login key written by | Upgrades to v2? |
|---|---|
| `register` — `server/src/handlers.rs` (~1188) | yes, hybrid required |
| `change_password` — `server/src/handlers.rs` (~2247) | yes, hybrid required |
| **`login` — `server/src/handlers.rs` (~1370–1390)** | **no — verifies only, never writes** |

And `static/crypto.js` `loginRequestBody()` only attaches `login_pq_signature` when the
*stored* key already starts with `{` (v2 JSON). So a legacy account signs with Ed25519
alone forever, leaving recorded login signatures quantum-vulnerable — the exact
harvest-now-decrypt-later hole this work exists to close.

**What was implemented:**

1. `static/crypto.js` `loginRequestBody()` — for a bare (v1) `login_public_key` it now
   attaches `login_public_key: deriveLoginPublicKeyBundle(...)`, guarded by try/catch so a
   missing PQ library leaves a legacy account working as it was rather than blocking login.
2. `server/src/handlers.rs` `LoginRequest` — gains the optional `login_public_key` field.
3. `server/src/handlers.rs` `login` — after the signature verifies against the OLD key and
   before the 2FA branch, a v2 bundle is stored with `set_login_public_key` — but **only**
   if it repeats the exact Ed25519 half that just verified. That check is what stops a
   captured login request from being turned into a key swap.
4. `tests/pq-envelopes.spec.ts` — new `lazy login re-keying (PQ Phase 3)` describe:
   `a legacy Ed25519-only account upgrades to hybrid on its next login` (downgrade the
   row to a bare key, log in, assert v2 stored with the same Ed25519 half, then assert an
   Ed25519-only login is refused with 401) and `a bundle with a different Ed25519 half is
   ignored` (login still succeeds, stored key never changes).

**Verified:** both new tests pass. Across two runs all nine tests in the spec have
passed, but not in a single run: the pre-existing `registration publishes the derived
ML-KEM identity key` flaked once on a missing `#show-register` selector and then passed
standalone in 6s.

Also required by the same decision: **no legacy fallbacks anywhere.** Confirmed already
enforced — `verify_user_verifier` accepts only `$e2e$…` and `verifier_needs_upgrade` was
deleted. Keep it that way; the app is in development and there are no real users.

## N2. Environment: this volume corrupts Rust build artifacts

Not a code task, but it will waste a session if rediscovered. `/mnt/stocare` is **exFAT**,
and cargo builds on it fail in three distinct ways:

- `ETXTBSY` executing freshly written build scripts — retries succeed.
- `couldn't read .../build/serde-*/out/private.rs: stream did not contain valid UTF-8` —
garbage written into build output.
- `found invalid metadata files for crate ...` and cargo itself panicking in
`src/tools/cargo/src/compiler/custom_build.rs` — corrupt `.rmeta` from a partial build.

**Workaround used here:** put the target directory on a native filesystem and point cargo
at it, e.g. `CARGO_TARGET_DIR=$HOME/.cache/e2e-target cargo build --release`. The launcher
honours that variable (`start-server.sh`), and Playwright's `webServer` inherits it from the
shell that launches the run. `server/target` (1.9 GB of corrupt artifacts) was deleted;
the default path is still `./target`.

Also note `core.fileMode=false` here: a newly added script lands as `100644` even after
`chmod +x`, so use `git update-index --chmod=+x` and re-check with `git ls-tree HEAD <path>`.

The same redirect also broke the test suite: 16 call sites across 11 specs spawned their
isolated server from a hardcoded `server/target/release/e2e-chat`, so on this checkout they
died with "server binary not found" (and on Windows that path no longer exists at all). They
now resolve it through `tests/_server-binary.ts`, in the same order as
`scripts/target-dir.sh`: `CARGO_TARGET_DIR`, then the config's `target-dir`, then `target`.
That alone turned `kill-switch.spec.ts` from 8 passed / 3 failed into 11 passed.
