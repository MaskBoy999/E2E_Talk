## Testing (Playwright)

- `webServer` config runs `cd server && cargo run` on port 3443 (HTTPS, `reuseExistingServer: true`). The server persists to `server/e2e_chat.db` across runs, so fixed test usernames accumulate and registration fails on reruns — always suffix usernames with a timestamp/random (e.g. `media_${Date.now().toString(36)}`).
- `selectedFiles` and `currentFileIndex` in `static/chat.js` are top-level `let` bindings: they are **not** on `window`. Read them inside `page.evaluate` via indirect eval: `(0, eval)('selectedFiles[currentFileIndex]')`. Function declarations (`_applyUploadTransformsToFile`, `checkUploadMagic`, `photoEditState`, `videoEditState`) ARE on `window`.
- The photo/video edit flows are async after clicking Confirm (canvas `toBlob` / video transcode). Tests must wait for the edit modal to hide before asserting on `selectedFiles`, or they read the stale original file.
- Pre-existing broken suites (unrelated to uploads): `media.spec.ts` fails because its tests `goto index.html` without logging in (redirects to login.html) and expect DOM elements that require auth; `security-hardening.spec.ts` G2 fails on its isolated-server port guard, G4 on a persisted admin password. G5 (client-side magic-byte validation) is the upload-relevant one and passes. `grouped-files.spec.ts` fails 12 tests for the same reason (several `goto index.html` without auth, plus `#attach-btn` filechooser timeouts) — verified identical with all static changes stashed.
- `str_replace` edits are line-ending agnostic and rewrite matched regions in the file's dominant style — no need to fight CRLF vs LF.

## Upload edit system (static/chat.js)

- Chrome MediaRecorder webm files report `duration = Infinity` in a fresh `<video>` element. The export pipeline (`_videoExport`) and any duration probe must resolve it by seeking far (`v.currentTime = 1e7`) — the browser clamps and exposes the real end. A no-op seek (`currentTime = 0` when already 0) never fires `seeked`, so wait for the seek by polling `currentTime`/`seeking` rather than the event.
- Video export must actually `play()` the source while recording: frames are drawn as playback advances, and the frame loop should be rAF-polled (draw only when `currentTime` changed) — `requestVideoFrameCallback` can stall on detached video elements.
- Exported webm `File`s must use plain `type: 'video/webm'` (no codec params) and a `.webm` name so `getCorrectMimeType` + the G5 magic-byte check agree. Quick-action mirror/rotate on the upload preview is CSS-only; the real file transform happens at upload in `_applyUploadTransformsToFile` (images: canvas re-encode; videos: full `_videoExport` transcode). Editing in a modal clears that file's quick-action state to avoid double transforms.
- The photo draw canvas can shift vertically mid-stroke when the "Confirm/Discard drawing" bar appears (flex layout change), desyncing pointer coordinates — cache `canvas.getBoundingClientRect()` at stroke start and reuse it for the whole stroke.
- Crop overlays are sized in JS to the canvas's displayed rect (`_photoSyncOverlay`/`_videoSyncOverlay`) because the canvas is CSS-scaled; box coords are CSS px mapped by `canvas.width / overlay.clientWidth`. Show the modal (`display:flex`) BEFORE initializing the crop overlay or its rect is zero. Video crops are stored in full-frame coordinates and must be re-mapped on rotate/mirror (`_transformCropRect`); applying a second crop offsets from the existing one.
- The photo edit modal and video edit modal are intentionally not in the click-off/Escape modal close lists — they can only be closed via Cancel/Confirm.
- Video edit UX conventions: the modal opens with NO tool forced (no crop overlay), applying a crop exits crop mode (`_videoSetTool(null)` — never re-arm a fresh box, or users get a confusing second crop from an unexpected position), and the final Confirm auto-applies an open crop box so the upload matches the editor view. A live PiP crop preview (`#video-crop-preview`, `_videoUpdateCropPreview`) redraws the exact boxed region of the edit canvas; it refreshes through `_videoSetCropBox` (the single funnel for init/drag/W-H inputs) and `_videoRenderFrame`, and hides whenever `s.tool !== 'crop'` or the overlay is hidden.
- Video crop rendering must NOT compute the crop offset with the centering term (`(fw-outW)/2 - crop.x`): that shifts the region and goes black for corner/edge crops. `_videoDrawFrame` instead renders the full rotated/mirrored frame to a reused offscreen canvas (`_videoGetFullFrameCanvas`) and extracts the crop rect 1:1 — the same code path serves the editor canvas (`_videoRenderFrame`) and the export (`_videoExport`'s draw loop), so the preview is pixel-identical to the upload. The photo editor was never affected (it extracts via `getImageData`).
- `_videoExport` refuses to start the MediaRecorder until a decoded frame is actually on the canvas (`canvasHasContent` checks alpha): starting while the detached video element is still decoding records black frames.
- Playwright can assert "the video really plays" by sampling pixels at several fractions of the resolved duration (non-black), and by locating the test video's moving white dot (brightest column moves between two times). To capture the exact sent bytes, stub the global `window.uploadFileToServer` before clicking `#confirm-upload` and analyze the captured `File` (the app calls it bare, so the global override wins).
- The photo-video-edit suite takes ~10 minutes (real-time video transcodes); run it in the background (`nohup ... > log 2>&1 &`) and poll the log instead of waiting synchronously.
- CaptureStream-produced webm can report `duration = null` (NaN), not just Infinity — same far-seek fix applies. In the video editor, `_videoResolveDuration` must run AFTER `_videoSetTool(null)` at open: the tool reset calls `_videoCutStopPreview()`, whose seek back to `cutStart` silently cancels the pending far-seek, leaving the duration unresolved forever (the cut ruler then shows a bogus 1-second scale). `_vFmt` guards NaN.
- Video cut preview (`_videoCutTogglePreview`/`_videoCutStopPreview`): unmutes the hidden `#video-edit-source`, plays the [cutStart,cutEnd] range looping (seek back when `currentTime >= endT`), renders frames via rAF, and is stopped on drag start, tool switch, transform, undo/redo, and modal close. The seconds ruler (`_renderCutRuler`) is shared with the audio editor.
- The video cut track has a frame-strip preview (`#video-cut-strip`, `_videoBuildCutStrip`): it samples ~W/60 frames across the duration by sequential promise-chained seeks (`_videoSeekTo` has a 700ms timeout fallback because a no-op seek never fires `seeked`), drawing each cell aspect-fit from the SOURCE video (scrubbing aid, not WYSIWYG). It is guarded by `s._stripBuilt` (reset per video in `openVideoEditModal`) and `_videoStripBusy`, only builds when the timeline is visible AND the duration is resolved (webm Infinity), triggers from `_videoSetTool('cut')` and lazily from `_videoCutRefreshUI` (which runs again after `_videoResolveDuration`), and parks the video back at cutStart when done. The video track is 52px tall (`#video-cut-track` override) vs 36px for audio; `.video-cut-range` got `z-index:2` so it paints above the strip, which is `pointer-events:none`.
- The audio editor (`audioEditState`) is state-only until Confirm: `encodeEditedAudio` applies cut+reverse+gain in one pass while **preserving the source format when the browser can encode it** — webm re-encodes in real time via MediaRecorder `audio/webm` (opus); mp3 attempts WebCodecs `AudioEncoder('mp3')` and wraps raw frames in a minimal ID3v2 header via `_mp3WithId3`; **Chromium registers the mp3 codec (configure succeeds) but rejects encoding — the encode throws "Unsupported codec type", so mp3 and ogg (no browser encoder at all) fall back to `encodeEditedWav`** (stereo 16-bit PCM; mono `encodeTrimmedWav` is the notification/ringtone-only encoder). Preview uses Web Audio (`playbackRate = -1` + `start(0, end, len)` for reverse; `createGain` for volume), and the AudioContext is created per modal open and closed on close. Audio files get only the Edit quick action (mirror/rotate hidden). `_audioCutInit` re-registers `onmousedown` idempotently on every open, so it is called from `openAudioEditModal`, not the static init. `audio/webm` is in `UPLOAD_MAGIC_SIGNATURES` (EBML `1A 45 DF A3`). Note: chat.js only loads on index.html, not login.html — window-level unit tests of chat.js functions must run after `registerAndSetup`.
- WebCodecs probe results (Playwright Chromium): `AudioEncoder` supports **opus** end-to-end; `mp3` configure succeeds but encode throws `NotSupportedError: Unsupported codec type`; `flac`/`aac` are unsupported. MediaRecorder `audio/webm` is supported. Tests that record audio in-page must create an AudioContext and `await ctx.resume()` — a context created in `page.evaluate` (no user gesture) starts suspended.

## Media viewer & theme settings

- The media viewer (`openMediaViewer`/`setupVideoControls` + `setupAudioControls`) is the app-wide media player. Its control bars are CLONED + replaced on every setup call (`#video-controls`, `#audio-controls`), so new buttons must live in `static/index.html` and be re-wired inside those functions each time; loop state resets per media item (fine). Loop buttons: `#vc-loop`/`#ac-loop`, toggling `video.loop`/`audio.loop` with an `.active` class as the ONLY indicator (accent color + tinted background — the user explicitly rejected a "Loop on" text chip). Inline audio previews in messages (`loadMediaPreview`'s isAudio branch) use native `<audio controls>` and DON'T open the media viewer, so they got their own custom loop toggle (`.inline-loop-btn` next to the player) — the audio loop button in the viewer is otherwise only reachable via mixed-media gallery navigation.
- Display settings theme swatches (`.theme-swatch` under the accent/background color rows) are PASSIVE previews of the chosen palette — do NOT make them clickable (the user explicitly asked to revert that; they are not buttons). The `.video-ctrl-btn.active` / `.inline-loop-btn.active` styles deliberately share the accent color so active states read clearly. On fresh load with no saved theme the hex inputs used to stay EMPTY next to a populated picker — they now initialize from `picker.value` when there's no saved value (kept, unrelated to the swatch revert).
