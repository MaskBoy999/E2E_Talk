# E2E Talk encryption and project handoff

This document describes the encryption system currently implemented in this repository as of July 2026. It is intended as a practical handoff for developers and other AI agents. It describes the code as it exists, not an aspirational security claim.

## Security model in one paragraph

Direct messages and server-channel messages are encrypted in the browser before they are sent. The Rust server stores and relays ciphertext, nonces, public keys, and metadata; it does not receive the plaintext or an identity private key. A database leak or an API caller without a participant's private key cannot decrypt message bodies. This is end-to-end encryption against an honest-but-curious server and storage/network attackers. It is **not** a complete Signal-style protocol and it does not protect against a server that maliciously serves modified JavaScript to a browser.

## Cryptographic implementation

All browser cryptography is implemented in `static/crypto.js`.

- Identity agreement: X25519-style elliptic-curve Diffie-Hellman implemented in JavaScript using BigInt arithmetic.
- Key derivation: HKDF-SHA-256. DM keys use the context string `e2e-dm-v1:<dm-channel-id>`.
- Message encryption: XChaCha20-Poly1305-style authenticated encryption helpers in `crypto.js`. Ciphertext includes an authentication tag; modification or use of the wrong key causes decryption to fail.
- Randomness: the crypto module's random-byte helper is used for private keys and nonces.
- Encoding for transport/storage: binary values are Base64 strings in browser/server JSON payloads.

The project currently has its own JavaScript crypto implementation. Do not casually change byte encoding, nonce sizes, HKDF labels, or curve operations: doing so makes existing ciphertext unreadable. For a production security product, replace/review this implementation with a mature audited cryptographic library and protocol rather than extending custom protocol code.

## Identity keys and local storage

An account identity is a 32-byte private key plus its derived public key.

- A new identity is generated by `static/auth.js` during registration.
- The key is persisted only after the registration API succeeds.
- Keys are stored per account ID in browser localStorage:
  - `e2e_identity_private_<user-id>`
  - `e2e_identity_public_<user-id>`
- `E2ECrypto.getIdentityKeyPair()` resolves the active account from `localStorage.user`; `saveIdentityKeyPair()` can also receive an explicit account ID.
- The old global keys, `e2e_identity_private` and `e2e_identity_public`, are only migrated when their public key exactly matches the server's public key for the account. This prevents a key from another account in the same browser profile being claimed accidentally.

The key is never posted to the server. The server receives the public half during registration and stores it in `users.identity_public_key` (with supporting historical/multi-device public-key data in `user_public_keys`).

### Login and device linking behavior

Normal username/password login does not generate an identity key. If the account has no local identity on that browser, `static/chat.js` clears the session and returns to login with an instruction to use **Connect with Local Key**. This is deliberate: silently making a new key would make existing encrypted data unreadable and can cause identity confusion.

The current link flow accepts a manually transferred local/private key. It derives the public key on the new device and compares it to `/api/identity/<user-id>`. Only an exact match is accepted. It then saves the private key locally under that account ID; it does **not** call `/api/identity/upload`, so a link cannot replace the account's registered key.

This is a same-identity-on-multiple-devices model. Copying the local key remains sensitive: anyone who obtains it can impersonate/decrypt as that account. A future design should use independently generated device keys and QR-approved device linking.

## Direct-message encryption flow

DMs use a deterministic shared secret derived from both participants' current identity keys.

1. The sender is authenticated to the server and has a local identity private key.
2. The sender fetches the other user's public key from `GET /api/identity/:user_id`.
3. `E2ECrypto.encryptDm(plaintext, dmChannelId, myPrivateKey, otherPublicKey)` computes X25519 ECDH, derives a 32-byte key with HKDF, then encrypts the plaintext.
4. The browser sends `{ type: "dm_send", dm_channel_id, encrypted_content, nonce }` over the authenticated WebSocket.
5. The server stores ciphertext and nonce in `dm_messages`; it broadcasts the same encrypted payload to DM members.
6. A receiver fetches the sender/other participant public key, repeats ECDH/HKDF using its local private key, and calls `decryptDm`.

The same key is derived by both sides because ECDH is symmetric:

`ECDH(A_private, B_public) == ECDH(B_private, A_public)`

The DM channel ID is included in HKDF context, so a key derived for one DM channel is not reused directly for another channel.

Relevant client functions:

- `loadDmMessages` and `appendDmMessage` decrypt stored DM ciphertext.
- `sendDmMessage` fetches the recipient key and encrypts immediately before WebSocket send.
- The live WebSocket handler decrypts `dm_new` events for the selected DM.

Relevant server code:

- WebSocket message handling: `server/src/ws.rs`
- DM REST handlers: `server/src/handlers.rs`
- DM persistence: `server/src/db.rs`, `dm_channels`, `dm_members`, and `dm_messages` in migration `004_friends_dms.sql`.

### Important current DM limitations

- There is no Double Ratchet, pre-key handshake, forward secrecy, post-compromise recovery, or per-message key deletion.
- A long-term identity-private-key compromise can decrypt recorded DM traffic that was encrypted with that identity pair.
- The API returns a single `identity_public_key` to current DM code even though the server also has a list of public keys. It is not yet true independent multi-device encryption.
- Bad historical messages created while an account was using another account's old global key cannot be repaired without the private key actually used at send time.

## Server-channel encryption flow

Servers use a random symmetric server key. That key is stored locally by members and envelope-encrypted for each member's identity public key on the server.

1. When a server is created, the owner generates a random server key in `chat.js`.
2. Each channel derives a channel-specific key from that server key; messages are locally encrypted before WebSocket send.
3. The owner encrypts/envelopes the server key for each member identity and uploads the encrypted envelope to `/api/servers/:server_id/keys`.
4. A joining member downloads its envelope and decrypts the server key with its identity private key.
5. Key rotation creates a new server key and envelopes it for remaining members, for example after a member is kicked.

Old local server keys are retained as history so older ciphertext can still be opened after rotation. This is convenient but means a device that retains old keys can still read old messages; it is not retroactive revocation.

## Friend requests and authorization

Friend codes are generated client-side, but only their SHA-256 hashes are sent/stored. A friend request requires the code, and DMs can only be created between accepted friends.

`friend_requests` has one row per directed pair. Declining a request changes its status to `declined`. `Database::create_friend_request` now reopens that declined row as `pending`, resets its timestamps, and re-notifies the recipient instead of failing against the unique constraint. Pending duplicates still fail, and accepted friends cannot send another request.

## Trust boundaries and threat model

Protected by the current design:

- Someone who steals the SQLite database sees ciphertext rather than DM/channel plaintext.
- A normal API caller who is not a conversation participant cannot retrieve arbitrary DM messages due to authorization checks.
- A random identity key cannot decrypt a captured DM ciphertext; tests exercise this case.
- The server does not receive client identity private keys through registration or the current linking flow.

Not protected, or only partially protected:

- A malicious web host can serve altered `crypto.js`/`chat.js`, capture plaintext in the browser, or substitute public keys. HTTPS protects transport from third parties, not a server that controls the application bundle.
- Browser localStorage is readable by JavaScript executing on this origin. An XSS vulnerability, malicious extension, shared unlocked profile, or local malware can steal identity private keys.
- The current static ECDH DM scheme lacks forward secrecy. Do not call it Signal-equivalent or "perfectly secure".
- Metadata remains visible to the server: accounts, friends, DM/channel membership, timestamps, ciphertext sizes, and likely online/WebSocket activity.
- The manual local-key linking mechanism exposes a high-value private key to clipboard/paste. Treat it as a recovery secret, never as a casual shareable token.

Recommended hardening order:

1. Serve only over HTTPS with a strict Content Security Policy and dependency integrity controls.
2. Move key material from plaintext localStorage toward Web Crypto non-extractable `CryptoKey` objects in IndexedDB where practical; this helps against simple extraction but does not defeat XSS running in the app origin.
3. Replace manual private-key copying with QR-approved linking and distinct per-device public keys.
4. Encrypt every outgoing message for every active recipient device and sender companion device.
5. Adopt an audited X3DH/PQXDH + Double Ratchet implementation, with identity/safety-number verification and key-change warnings.
6. Consider key transparency so a malicious key directory is detectable.

## Project map for future agents

This is a Rust/Axum backend plus static HTML/CSS/JavaScript frontend. There is no front-end build system.

| Location | Responsibility |
| --- | --- |
| `static/index.html` | Main authenticated chat UI and modals. |
| `static/login.html` | Login, registration, and local-key connection UI. |
| `static/auth.js` | Registration/login/local-key link behavior. |
| `static/chat.js` | UI state, server/channel/DM behavior, WebSocket operations, encryption call sites, friend-request badge. |
| `static/crypto.js` | Browser crypto primitives, identity/server-key persistence, DM and channel encryption. |
| `static/style.css` | All UI styling. |
| `server/src/main.rs` | Axum routes and static file serving. |
| `server/src/handlers.rs` | HTTP API handlers and authorization. |
| `server/src/ws.rs` | Authenticated WebSocket protocol and live message delivery. |
| `server/src/db.rs` | SQLite operations, migrations, friendship/DM/server storage behavior. |
| `server/migrations/` | SQLite schema. `004_friends_dms.sql` is the friend/DM schema. |
| `tests/chat.spec.ts` | Broad Playwright coverage for servers, channels, encryption storage, admin, membership. |
| `tests/dm.spec.ts` | DM, friend request, identity isolation, and ciphertext privacy tests. |

### Startup and testing

- Backend: from `server`, run `cargo run` (or use `start-server.bat` from repository root). It serves on `http://localhost:3000` by default and uses `server/e2e_chat.db` unless environment variables override it.
- Browser tests: from repository root, run `node_modules\\.bin\\playwright.cmd test` in PowerShell if execution policy blocks `npx`.
- Rust validation: run `cargo check` or `cargo build` from `server`.

Recent regression coverage in `tests/dm.spec.ts` verifies:

- two new users can become friends and exchange decryptable DMs;
- server/API DM storage returns ciphertext and nonce, not a plaintext `content` field;
- a newly generated unrelated identity cannot decrypt captured DM ciphertext;
- registering two accounts in one browser profile preserves each account's private key when switching back;
- a declined request can be sent again.

## Rules for safe future changes

- Never auto-generate or auto-upload a new identity key for an existing logged-in account.
- Never put an identity private key in a server request, database field, log, error message, or test fixture output.
- Treat changes to `crypto.js`, identity storage names, encryption formats, and public-key APIs as compatibility and security changes; add migration/tests first.
- Test both directions of every DM scenario, then test reload and a second browser context.
- Keep server-side checks strict: only DM members may access DM data; only intended account/device owners may register keys.
