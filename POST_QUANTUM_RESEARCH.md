# Post-quantum deep research — 0.2.44 rollout re-check

**Date:** 2026-10-06 · **Method:** repo-verified code paths and lockfile versions,
plus a dated upstream/advisory check. This is the working research note that sits
under `POST_QUANTUM_AUDIT.md`; where the two disagree, the corrections in §2 are
newer and supersede the audit text.

**Headline:** the shipped hybrid layer is correctly implemented *at each call
site*, but its two root keys are still classical-only in a way that hands a
harvest-now-decrypt-later (HNDL) adversary the hybrid protection back:

1. **HIGH-1** — the ML-KEM identity key is derived from the X25519 identity
   private key, so breaking X25519 (Shor) recovers the ML-KEM key too.
2. **HIGH-2** — DM messages and DM calls key off a classical X25519 ECDH
   (`getDmKey`) with no PQ leg at all.

Everything else found is medium/low and listed with exact fixes below.

---

## 2. HIGH-1 — the ML-KEM identity seed is derived from the X25519 private key

**Where.** `static/crypto.js:254-257`:

```js
function pqIdentitySeed(identityPrivateKey) {
    var priv = new Uint8Array(identityPrivateKey);
    return hkdf(priv, priv, PQ_IDENTITY_LABEL, 64);   // 'e2e:pq-identity-seed:v1'
}
```

`getIdentityPqKeyPair` turns that seed into the ML-KEM-768 identity keypair, and
`envelopeEncrypt` upgrades every **self**-wrap to v2 with it. The identity X25519
keypair itself is a random key generated at registration
(`crypto.js:454,919-933`) and synced in the encrypted key bundle.

**Attack.** An adversary records `identity_public_key` (it is on every key
bundle/envelope) plus any v2 envelope (or the notification escrow, which units
the same identity keys). With a CRQC: Shor → X25519 private key → HKDF seed →
ML-KEM-768 secret key → decapsulate the recorded KEM ciphertext → same HKDF
output the sender derived → plaintext. **The PQ half adds nothing**; the
envelope is effectively v1 against HNDL.

**Impact.** This is the root of most of the app: DM/server/file keys are wrapped
to identity keys, notifications escrow to them, and self-wraps of channel keys
use them. So the audit's §0/§1.3 statement — *"Security holds unless **both**
X25519 and ML-KEM break"* — is **wrong** for every identity-keyed envelope, and
the correct security level today is X25519-only (classical). The login layer is
the exception: its ML-DSA seed comes from `(hash_key, password)`
(`crypto.js:576-636`), not from the X25519 key, so it does not inherit this
flaw.

**Fixes, with breakage analysis.**

* **Fix A (recommended, keeps multi-device).** Generate an independent random
  64-byte PQ seed once per account, store it in the key bundle next to
  `e2e_identity_private_*` (localStorage + the encrypted server blob), derive
  ML-KEM from it, publish the public half as today. Nothing is derivable from
  the X25519 key any more.
  * Blast radius: key-bundle version (`BUNDLE_VERSION` 4 → 5) and its
    `BUNDLE_KEY_TYPES` list, `identity_pq_public_key` registration payload,
    `POST /api/identity/pq-key`, `tools/gen-pq-kat.mjs`, and the test
    *registration publishes the derived ML-KEM identity key* (renamed: it now
    publishes a random one).
  * Migration: keep the old derived key readable for a window, publish the new
    one, re-wrap self-held keys with it; after peers re-read
    `/api/identity/{id}` nothing old is needed. Add a v3 envelope marker so a
    sender can tell "recipient has only the old key" from "recipient has the new
    seed"; drop the old key when the window closes.
* **Fix B (no new storage).** Derive the seed from a secret that Shor cannot
  recover — the vault/hash-key material with a distinct label
  (`e2e:pq-identity-seed:v2` over `hash_key`, not over the X25519 private key).
  * Cost: every device needs the hash key (i.e. must have completed login /
    vault unlock) before it can read v2 envelopes; pairing devices that restore
    only the identity key lose the PQ half until unlocked. Same dual-read
    migration as A.
* **Fix C (pre-release shortcut).** Since v2 shipped only in 0.2.44 and the
  project is pre-release (the audit explicitly allows breaking migrations),
  change the derivation to anything not derived from X25519 and accept that
  pre-fix v2 envelopes stop decrypting. Cheapest, no dual-read window; only
  viable if no real v2 traffic exists. This is a one-place change plus the
  test/fixture updates from Fix A.

Verification for any of them: a new KAT asserting the ML-KEM secret key is
**not** a function of the X25519 public/private key bytes (e.g. two accounts
whose X25519 keys collide must not collide in ML-KEM — assert
`pk(X25519) ⇒ pk(MLKEM)` is not reproducible from the public key), plus a
round-trip test that the recorded-envelope attack (derive PQ from X25519) no
longer yields the plaintext.

## 3. HIGH-2 — DM messages and DM calls have no PQ leg

**Where.** `static/crypto.js:848-856`:

```js
function getDmKey(dmChannelId, myPrivateKey, otherPublicKey) {
    const shared = x25519SharedSecret(myPrivateKey, otherPublicKey);
    const key = hkdf(shared, shared, 'dm-channel:' + dmChannelId, 32);
    ...
}
```

Used for DM messages/attachments/profile payloads (`chat.js` ~1073, 14738,
23019, 33727) and — the one that is easy to miss — the **DM call room key**:
`voice.js:884` derives it for `voice:` signalling and the app-layer media frame
encryption (`voice.js:10838` encrypt, `voice.js:11039` decrypt with
`S.roomKeyB64`). Server-channel call room keys come from the channel key (which
is wrapped hybrid — subject to HIGH-1); DM calls do not get even that.

**Attack.** Record DM ciphertexts + both parties' identity public keys (public),
break X25519 with a CRQC, recompute `dmKey` and the room key → DM history and
recorded DM call media decrypt.

**Fix.** Version the DM key. The pragmatic shape in this codebase:

```
dmKey_v2 = HKDF(dh || ml_kem_ss, salt = dh, info = "dm-channel-v2:" + dmChannelId, 32)
```

where `ml_kem_ss` comes from a one-shot ML-KEM encapsulation carried by the side
that already provisions the DM (or, simpler, generate a random DM key once and
deliver it in a hybrid envelope, exactly like `server_keys` do). Keep
`dm-channel:` for reading old messages.

* Blast radius: `encryptDm`/`decryptDm`, the DM message `AAD` (must carry the v2
  marker or a downgrade is possible), encrypted sender usernames
  (`crypto.js:1310`), forwarded-DM payloads (`chat.js:21031,21058,21163,21193`),
  DM profile payloads (`chat.js:33729`), DM call key (`voice.js:884`) and the
  `voice-signal` AAD (`voice.js:917-933`).
* Note: `getDmKey` is deterministic on purpose (multi-device), so this stays a
  static-key scheme — forward secrecy is the ratchet/MLS phase, not this fix.

## 5. Medium findings and fixes

**MED-3 — silent v1 fallback on the envelope path.** `envelopeEncrypt`
(`crypto.js:163-181`) upgrades a self-wrap to v2 only `if (pqAvailable() …)`,
and the derivation failure is swallowed in a bare `try/catch (_) {}`. The
vendored modules are dynamic-imported at page load (`pqReady()`), and the two
files are **not** in `sw.js` `STATIC_ASSETS` (grep: no `libs/` or `noble`
entry) — they are only picked up by the stale-while-revalidate runtime cache.
So a cold/offline start, a CSP hiccup, or a load race can silently write v1
self-wrapped keys (channel keys, notification sounds, soundboard clips) at the
exact moment they become at-rest HNDL material.
*Fix:* add the vendored closure to `STATIC_ASSETS`; make the key-wrapping paths
await `pqReady()` (or retry and re-wrap on next load — the identity-key
republish pattern already exists); log/telemeter the fallback instead of
silence.

**MED-4 — legacy v1 at-rest envelopes are never re-wrapped.** v1 stays readable
forever by design, but nothing migrates the *stored* v1 envelopes (server keys,
file keys, self-wraps) after the v2 rollout, so the DB keeps HNDL-material
indefinitely. *Fix:* a one-shot re-wrap sweep on next load (decrypt v1, re-wrap
v2, replace the stored row) with a decommission date for v1 read support.

**MED-5 — legacy Ed25519-only login is accepted indefinitely.** The server
verifies a bare `login_public_key` (v1) when no v2 blob is present, so an
account that has not re-keyed stays forgeable by a CRQC. The audit defers this;
pre-release is the cheapest time to force it. *Fix:* flag legacy accounts at
login, force a re-key (the client already derives the v2 key from
`(hash_key, password)`), and after a window remove the v1 verification path.
*Test:* the existing *v2 account refuses an Ed25519-only login* case gets a
companion: *a legacy account is upgraded on next login and then refuses v1*.

**MED-6 — the pinned rustls sits inside a patched advisory window.** rustls
0.23.42 (our pin) is affected by **GHSA-2mjx-qc3c-rqvc** — TLS 1.3 handshake
messages sent at the wrong encryption level, after a key-changing message in
the same record, were accepted; fixed in **0.23.45** (2026-09-14). The
handshake transcript remains authenticated, so this is not a confidentiality
break, but it is a protocol defect a peer could exercise and the fix is a
patch-level bump. *Fix:* `rustls = "0.23.45"` (and re-run
`tests/pq-envelopes.spec.ts` → *the server negotiates the X25519MLKEM768 hybrid
group*, since the provider/feature set moves with the bump).

**MED-7 — no dependency-CVE gate in CI.** `.github/workflows/` has
`android.yml` and `release.yml` only; the early-2026 ML-DSA CVEs and the rustls
advisory above show the drift risk — MED-6 would have been caught on the day it
shipped. *Fix:* add `cargo audit` (or `cargo-deny`) plus a scheduled
`cargo update --dry-run`/`npm audit` job, and a watch list for `ml-dsa`,
`ml-kem`, `rustls`, `aws-lc-rs`, and the vendored noble closure.

## 6. Low / residual

- **LOW-7 — vendored library is self-audited only.** Accepted for now (hybrid:
  X25519 still gates security once HIGH-1 is fixed). Revisit on an independent
  audit or when WebCrypto ML-KEM ships.
- **LOW-8 — best-effort zeroization.** `_secureZero` in JS cannot guarantee
  erasure; treat key material in the page as exposed for the page lifetime.
- **LOW-9 — residual lanes unchanged:** DTLS-SRTP (browser), RFC 8291 (spec),
  certificate PKI (now actionable via rustls 0.23.44 + ML-DSA, above),
  metadata/traffic analysis (not a PQ problem), endpoint compromise (out of
  scope).

## 7. Suggested fix order

1. **HIGH-1** as Fix C (pre-release) or Fix A — one client change plus
   fixture/test updates; every other envelope-layer guarantee depends on it.
2. **HIGH-2** DM key v2 + DM-call room key; the largest surface (messages,
   forwards, sender usernames, profile payloads, voice signalling).
3. **MED-6** rustls 0.23.42 → 0.23.45 (patch bump, independent of everything
   else); **MED-3** (precache + await/repair), **MED-4** (re-wrap sweep),
   **MED-5** (forced re-key), all cheap and independent.
4. **MED-7** CI gate; then the rustls 0.23.44+ ML-DSA certificate evaluation
   for the pinned clients.

### Corrections this research makes to `POST_QUANTUM_AUDIT.md`

- §0/§1.3 "security holds unless both X25519 and ML-KEM break" is **false for
  identity-keyed envelopes** while the ML-KEM seed derives from X25519 (HIGH-1).
- §1.3 "Covered call sites: … self-wrapped keys" is misleading: the self-wrap
  path is only v2 when the vendored module is already loaded (MED-3), and its
  PQ half inherits HIGH-1.
- §1.6 "app-layer frame encryption … the key agreement for it is X25519 via
  §1.3" — for DM calls the agreement is `getDmKey` (classical, no PQ leg),
  not §1.3 (HIGH-2).
- §1.2 "adopt ML-DSA-65 certificates when rustls/webpki support them — not yet
  the case as of this date" — rustls 0.23.44 enables ML-DSA certificates by
  default (Sep 2026); this is now a version bump away.
